# 基准实验 Q&A（2026-09-03 04:05 CST）

## 你的三个问题

### 1. 有没有早停机制？
有，但和"验证分平台期提前收工"不是一回事：
- **熵坍塌检测**：策略熵连续 20 步低于 0.15×ln(vocab) → 判定坍塌，带噪声（0.25）重启；最多 55 次，超过后不再早停，改为强扰动继续训练。
- **停滞自适应噪声**：最优分 500 步不前进 → 噪声自动加大（最高 2 倍）。
- 结论：训练**不会傻跑满预算**（坍塌会重启），但总步数是固定预算（TRAIN_STEPS），没有"平台期到了就收工"式早停。

### 2. 为什么没有断点重训？—— 其实是有的！
- **每 20 步自动存检查点** `checkpoints/ckpt_{品种}_step_N.pt`（含模型权重 + 最优公式 + 分数 + 步数，带 vocab 版本校验）；
- **最优公式每步实时写盘** `strategies/best_{品种}.json`，训练历史每步写 `training_history_{品种}.json` —— 就算进程硬崩，最优公式也丢不了；
- `train_file.py` **不加 `--from-scratch` 时，下次运行自动从最新检查点续训**（日志会打"从 ckpt 恢复，起始步=N"）。
- 所以：断开 → 重跑同一命令 → 自动续训，不是从头。

### 3. 为什么这次实验"从头跑"？
- 是我在实验脚本里**故意传了 `from_scratch=True`**：固定 seed 42 + 清空状态，做可复现的干净对照。这是实验设计，不是框架缺陷。

## 多 seed 问题（04:11 补充）

### 你的担心是对的
单 seed 的 argmax 确实不能保证质量——单次采样的最优可能是运气。这正是之前 P1 加固加了两道保险的原因：
1. **统计闸门**：空模型 99 分位（冠军 val 必须显著超过 64 条随机公式） + 跨折 SE 裕度（冠军 vs 次优要拉开 >1×SE）——挡掉"单折碰运气"；
2. **多 seed 升级纪律**：`train_file.py --seeds A,B,C` 已实现——每个 seed 完整训练一轮（检查点/历史按 seed 隔离，互不干扰），**全部 seed 的 val 都超过旧冠军 + 0.02 裕度**才部署最佳者，任一不过就保留旧冠军。

### 多 seed 可行，成本账（当前机器负载）
- 每 seed ≈ 一整个训练：150 步 ≈ 3.5-4h；300 步 ≈ 7-8h；完整 9000 步 ≈ 5+ 天/seed
- 2 seeds ≈ 8h（一夜），3 seeds ≈ 12h——launchd 托管 + 断点续训，串行排夜跑完全可行
- 注意 holdout 单次消费：多 seed 各自验证，但只有最终部署那一次消耗（已按此设计）

### "放宽早停"——其实默认已经很松
引擎的"早停"= 熵坍塌检测（连续 20 步低熵 → 带噪重启，最多 55 次，之后强扰动继续），
**不是**"平台期提前收工"；搜索本身不会提前放弃，只是用重启换方向。可调的旋钮：
`ENTROPY_COLLAPSE_STEPS` / `ENTROPY_COLLAPSE_THRESH` / `MAX_RESTARTS` / `ADAPTIVE_NOISE`，
默认值就是给大搜索空间调宽的。真正决定效果的杠杆是 **步数预算 + seed 数**，不是早停参数。

## 多 seed 对训练是否有益？（04:15 补充——正面对答）

**结论先行：有益，但要看你问的是哪个层面——它对"部署置信度"帮助很大，对"这个数据集本身有没有 alpha"没有帮助。**

### 多 seed 真正解决什么：argmax 的轨迹方差
单 seed 的冠军 = 一条随机搜索轨迹上的 max(val)。这条轨迹的采样运气会直接影响谁当冠军。
K 个 seed 的升级纪律 = max 变 K 个独立轨迹的"全体共识"：任一 seed 的 val 没过旧冠军+裕度，就不部署。
效果是把"一次抽奖"变成"K 次独立抽奖都要中"——大幅降低部署一条轨迹运气公式的概率。

### 多 seed 不解决什么（重要）
- 不解决数据层面的过拟合：数据里若有虚假规律，所有 seed 都会找到它——共识挡不住数据集问题，
  那正是 holdout 闸门 + 空模型 + 数据指纹（单次消费）的职责。
- 不保证找到更好的公式：同样的总算力下，1 条长跑（含坍塌重启）可能比 3 条短跑找到更好的。
  多 seed 买的是"保守"，不是"更强"。

### 为什么本引擎多 seed 的边际收益比朴素管线小
本引擎已经有四道防运气机制，单 seed 并不裸奔：
1. 空模型 99 分位——冠军要和 64 条随机公式的分布比，单条轨迹的运气分会被打回来；
2. 跨折 SE 裕度——冠军必须拉开次优 >1×SE，挡"单折碰运气"；
3. holdout 单次消费 + 真实回测选优——最终部署要看从未参与选优的尾部窗口；
4. 熵坍塌重启（最多 55 次）——单次长跑内部已经在反复"换方向重来"，近似于 seed 内的多次独立搜索。
所以：多 seed 在本框架是"锦上添花"（把部署置信度从 95% 提到 99%），不是"雪中送炭"。

### 实际建议
- 当前**对比实验**（判断 BTC H1 能不能打）：单 seed + 统计闸门足够出第一结论，不用等多 seed；
- 若这策略要**上实盘**：跑 2 个 seed（不必 3+）做共识确认，成本 ≈ 多 4-8h 一夜，值得；
- 本引擎的多 seed 模式 `--seeds A,B` 已实现且按 seed 隔离检查点，跑法成熟，不存在可行性问题。

### 结论（04:15 用户决策）
单 seed 已够——对比实验阶段不跑多 seed，靠统计闸门（空模型 99 分位 + 跨折 SE + holdout 单次消费）防运气。

## 为什么不用向量化加速 / CPU 没吃满（04:35 补充）

**刚实测：训练进程 CPU 96-145%（8 核机器）≈ 只用 1-1.5 核。你的观察是对的。**

### 原因：瓶颈不是算子，是 GIL
- 每个算子的张量计算**已经是向量化的**（torch，unfold/滚动窗口）；
- 但每条公式的**Python 编排**全程持 GIL：遍历 4 个 WF 折 → 每折跑 8 步 VM → .item() 取数 → IC/惩罚/分数计算，
  这些 Python 代码把线程卡死，多线程并行评测反而更慢——仓库 config.py 里有当时的实测：
  `串行(intra=8) 21.8 s/步 vs 线程池 8×8 33.9 s/步(+55%)`，所以 PARALLEL_EVAL 默认 False。
- 算子太小（[1,65,9900] 级），释放 GIL 的张量时间抵不过线程切换 + 超订阅开销。

### 真正的加速路径（按性价比）
1. **进程池评测**（ProcessPoolExecutor）：绕开 GIL，每个 worker 独立解释器——仓库只测过**线程**，
   没测过**进程**。8 核理论上可望 2-4×。这是最值得先做的实验；
2. **批量公式求值**：同深度同算子的公式合并成 [B,C,T] 大张量一次跑（类似小编译器），根治但工程量大；
3. 削减每步 Python 开销：.item() / IC / 惩罚跨公式向量化，省一部分但不是数量级。
